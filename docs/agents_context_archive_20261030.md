## 全局规则（硬约束）

1. **分支**：日常开发与项目文档主要在 `main` 上维护，以 `origin/main` 为共享主线。因任务隔离、实验或保存参考项目修改等需要，可以创建和使用用途明确的命名分支，无需仅因使用其他分支另行请示；参考项目修改沿用 `refproj/<项目名>` 约定。切换或合并前检查工作区，保留已有改动，避免覆盖他人工作。
2. **共享服务器纪律**：服务器上有其他用户。除全局配置与 `/tmp` 这类不可避免的变动外，**不要在家目录下新增或修改其他目录**；不碰别人的家目录与容器；不修改系统配置、不重启 docker、不使用 `sudo`（需要特权操作时先问用户）。
3. **训练只在容器内跑**，不在宿主机直接跑 Isaac Sim / 训练；宿主机只做编排、检查与看门狗。
4. **`robot_description/` 只读**：MJCF、STL 及该目录内其他文件禁止修改，模型与物理参数一律不动；只有该目录 `README.md` 中**对机器人的文字描述**允许更新。
5. **本机不做训练**：桌面机只用于最后的效果验证（MuJoCo 等）。
6. **参考项目不进版本管理**：`reference_project/*/` 是上游快照与训练产物，被 `.gitignore` 排除；项目文档、配置与 PetBot 自有代码正常提交。
7. **不拿旧设备记录当基线**：桌面机上的历史运行记录（RTX 2080Ti 等）与训练无关，不作为任何结论依据。
8. **路径**：程序用相对路径加载模型与资源，不硬编码宿主机或容器绝对路径。
9. **文档写法**：根目录 `README.md` 面向人类，主要用于部署与使用，不同步实验进度；重要里程碑维护在本文件，实时进度和证据维护在当前交接页与对应实验文档。面向"下一个 agent"，只写结论与必要证据，不留对话痕迹；过时内容直接改掉或标明日期，不与新结论并列陈述。
10. **不确定就问**：规则之间若出现冲突，或需求含义不明，先问用户再动手。
11. **主动沉淀重要信息与进度**：agent 必须在交流、排查和实施过程中自行判断新增信息是否影响后续决策、执行或交接；凡涉及目标与背景、需求或约束变化、已确认的决策及依据、关键进展、实测结果、重要失败经验或阻塞项，都应及时同步到对应文档，不等待用户提醒，也不以完成代码修改为前提。符合下方收录标准的关键节点按日期写入本文件的[进度报告](#进度报告文档主线)，长期有效的信息更新到对应主题文档；同步修正受影响的旧表述。只保留结论与必要证据，区分用户确认、实测和待验证推测，不记录对话流水或无实质变化的重复检查。
12. **参考项目由 `default.xml` 清单管理**：`reference_project/` 下的项目通过 `repo` 物化。新增、删除或改变某个项目的 pin，必须在同一次改动中同步更新 `default.xml` 与 `reference_project/manifest.json`，保持清单与目录一致。
13. **参考项目的本地修改不能丢**：在服务器上跑 demo 时若改了某个参考项目的代码，要把**该项目**提交到本仓库的一个专用分支（命名 `refproj/<项目名>`，如 `refproj/recovery`），并把 `default.xml` 里该项目的 `remote`/`revision` 指向那条分支；在完成这一步之前，不要删除或覆盖那个 checkout。**为某个参考项目写的工具、脚本与实验定义**同样推到该项目的 `refproj/` 分支（如 `refproj/recovery-tools`，内容在 `tools/recovery_trial/`）；这类分支不写进 `default.xml`（它不是上游项目）。参考项目由 `repo sync` 按 `default.xml` 物化，**不要为取用参考项目或工具分支而切换主仓库工作区**；这不限制第 1 条允许的任务分支。

14. **PetBot demo 独立管理**：`demo_project/<项目名>/` 由同一 `default.xml` 通过 repo 物化，代码在 `demoproj/<项目名>` 分支版本化，main 不重复跟踪嵌套 checkout。修改前同步、完整修改后及时提交并推送；双端同一 demo 单端写入，训练固定 commit。清单、demo 索引与 manifest 同步维护；细则见[工程实施说明](docs/engineering_handoff.md#版本管理与双端协作)。正式项目 `rl_project/<项目名>` 同样由 repo 物化，分支为 `rlproj/<项目名>`，main只维护索引与manifest；预留训练目录不得提前塞入训练代码。

## 沟通与交付

- 只报告结论和最小必要证据，区分用户确认、实测、推测；避免重复检查和对话流水。
- 只读排查、常规文档同步和已授权任务所需的命名分支视为持续授权。其它副作用变更须有用户授权；文档维护本身不自动授权提交、推送或服务器操作。当前会话已授权项目整理及既有训练维护。
- 每次结束核对实际改动、影响、耗时和验证。训练代码变化要过容器内 PhysX/短训/重载的相应工程门槛；CPU 检查只能辅助，不能代替仿真。固定运行副本不得中途修改。
- 每轮迭代必须读取实际阶段、运动和关节轨迹，核对请求/执行/实测，抽查成功及失败样本；明显偏航、已落地仍卡阶段等动作缺陷不能被汇总成功率掩盖。审查项见[需求基线](docs/current_scope.md#每轮策略行为审查2026-10-27用户确认)。

## 目录职责与检查

| 路径 | 职责 |
|---|---|
| `robot_description/` | MJCF/STL 源模型，只读；仅 README 的文字描述可更新。 |
| `demo_project/<项目名>/` | `repo` 物化的 demo 源码，独立 `demoproj/` 分支；[upright 导览](demo_project/upright_rl_demo/README.md)列出三种训练入口。 |
| `demo_project/runs/` | 各批固定提交的独立副本、检查点、日志和评估轨迹；历史产物体量大，按当前状态文件定位，不整体遍历或清理。 |
| `rl_project/<项目名>/` | repo管理的正式项目，独立`rlproj/`分支；训练预留与sim2sim职责见[索引](rl_project/README.md)。 |
| `history/` | 忽略版本管理的后续归档位置；迁移前保留依赖清单，当前runs未搬迁。 |
| `reference_project/` | 上游快照及产物，不在主线重复跟踪。 |
| `robot_controller_demo/` | MuJoCo 恢复、跳跃前轮离地演示与姿态统计，不是策略训练仓。 |
| `docs/` | [当前交接](docs/current_handoff.md)、需求、工程、谱系和各批证据；按问题读取。 |

涉及重要变化时先更新对应主题文档，再视收录原则追加本表；无实质变化不写。旧研究资料在 `docs/reports/`，不作当前模型或训练基线。
